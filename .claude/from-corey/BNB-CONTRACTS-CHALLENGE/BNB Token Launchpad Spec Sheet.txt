Section 1: Protocol Mechanics and Economic Framework


This section establishes the complete economic and mathematical foundation for the decentralized token launchpad protocol. It details the bonding curve pricing model, the full lifecycle of a token from creation to decentralized exchange (DEX) listing, and the specific dual-fee structure that provides revenue for both the platform and token creators.

1.2. The Complete Token Lifecycle: From Inception to Decentralized Trading


The journey of every token launched on the platform follows a standardized, automated, and trust-minimized lifecycle composed of six distinct phases.
   * Phase 1: Creation
A user, the "creator," interacts with a central TokenLaunchFactory smart contract. They provide basic metadata for their token: a name, a ticker symbol, and an associated image URL. The factory contract then deploys a new, isolated BondingCurveToken contract instance. This process is entirely permissionless, significantly lowering the technical and financial barriers to token issuance.1
   * Phase 2: Initial Trading (Bonding Phase)
Immediately upon creation, the token is live and tradable directly against its dedicated BondingCurveToken contract. This contract acts as the sole counterparty for all initial trades. All "buy" transactions mint new tokens from the contract's pre-allocated supply, while all "sell" transactions burn the user's tokens. The price is determined algorithmically by the bonding curve as described in Section 1.1. This phase serves as the critical period for price discovery, initial distribution, and community formation.1 The total supply of each token is fixed at 1 billion, with a substantial portion (e.g., ~800 million) held by the bonding curve contract for sale.1
   * Phase 3: Graduation Trigger
The BondingCurveToken contract continuously monitors its internal state after every buy transaction. Specifically, it tracks the total amount of real BNB it has accumulated in its reserves. When this amount reaches a predetermined GRADUATION_THRESHOLD_BNB (e.g., 50 BNB), the "graduation" process is triggered. The contract's internal state transitions to Graduated, and the public buy() and sell() functions are permanently disabled, freezing the bonding curve.1
   * Phase 4: Automated Liquidity Provision
Once graduated, a new, publicly callable function, graduateToPancakeSwap(), becomes active. When invoked by any user, this function executes a pre-programmed sequence of actions. It takes a significant portion of the collected BNB reserves (e.g., 75%) and pairs it with a corresponding amount of the token's remaining unsold supply. It then programmatically calls the addLiquidity function on the official PancakeSwap V2 Router contract, creating the new public trading pair for the token.1
   * Phase 5: Trust-Minimization and Finality
This phase is critical for establishing user trust and preventing malicious actions. In the same atomic transaction as the liquidity provision, the BondingCurveToken contract performs two irreversible actions:
      1. LP Token Burn: It receives Liquidity Provider (LP) tokens from PancakeSwap, which represent ownership of the deposited liquidity. The contract immediately sends 100% of these LP tokens to a designated burn address (e.g., 0x00...dEaD). This permanently locks the liquidity in the PancakeSwap pool, making it impossible for the creator or the platform to withdraw it—the primary defense against a "rug pull".1
      2. Renounce Ownership: The contract renounces its own administrative privileges, making it fully immutable and severing any remaining control by the creator or the platform.
      * Phase 6: Public Trading
The token is now a standard BEP-20 asset, fully decentralized and trading on PancakeSwap. Its lifecycle on the launchpad platform is complete. The token's future is now determined by the open market and its community, entirely independent of the initial launch mechanism.


1.3. The Dual-Fee Distribution Model


A 2% transaction fee is applied to every buy and sell transaction conducted during the bonding curve phase. This fee is a core component of the platform's economic model and is split equally between the platform and the token creator.
         * Specification: The total fee will be 200 basis points (BPS), or 2%.
         * PLATFORM_FEE_BPS = 100 (1%)
         * CREATOR_FEE_BPS = 100 (1%)
         * On buy() Transactions: When a user sends BNB to purchase tokens, the contract first calculates the fee based on the incoming BNB amount (msg.value). 1% of the BNB is immediately transferred to the platform's treasury address, and 1% is transferred to the token creator's address. The remaining 98% of the BNB is then used in the bonding curve calculation to determine the number of tokens to be minted for the user.1
         * On sell() Transactions: When a user sells tokens back to the contract, the contract first calculates the total BNB value to be returned based on the bonding curve price. From this gross amount, a 2% fee is calculated. 1% is sent to the platform and 1% to the creator. The user receives the remaining 98% of the BNB.1
It is important to recognize the economic implications of introducing a creator fee. The original Pump.fun model prided itself on a "no creator tax" approach, which was central to its "fair launch" ethos, as it required everyone, including the creator, to buy into the token on the same terms.1 The inclusion of a 1% creator fee modifies this dynamic. It provides a direct revenue stream to the creator based on trading volume, which can be a powerful incentive for legitimate project founders to promote their token and foster an active market. However, this also introduces a new, subtle risk vector. A malicious creator could be incentivized to generate artificial trading volume (wash trading) to continuously extract their 1% fee from the contract's BNB reserves, thereby draining value from the ecosystem and the liquidity destined for PancakeSwap. While this specification will implement the fee model as requested, this trade-off between creator incentive and potential exploit must be acknowledged in the overall risk assessment of the platform.

Section 2: System Architecture: A Modular, Factory-Based Approach


The smart contract architecture is designed for security, scalability, and maintainability within the Ethereum Virtual Machine (EVM) environment. A modular, multi-contract design is mandated, leveraging the well-established Factory pattern. This approach isolates distinct functionalities into specialized contracts, enhancing security and clarity, which is a cornerstone of secure smart contract engineering.1


2.1. Architectural Overview: The Factory Pattern


The system's architecture is composed of two primary smart contract types:
         1. A Singleton TokenLaunchFactory Contract: This contract is deployed only once to the BNB Chain. It serves as the sole, trusted entry point for creating all new token markets on the platform.
         2. Multiple BondingCurveToken Contracts: Each time a new token is launched, the TokenLaunchFactory deploys a new, completely independent instance of the BondingCurveToken contract.
This Factory pattern is a deliberate choice that provides critical security and operational advantages in the EVM environment. It ensures that the logic, state, and funds of each token market are completely segregated at the contract address level. An exploit or bug in one BondingCurveToken contract cannot, under any circumstances, affect the funds or operation of any other token launched on the platform. This compartmentalization is fundamental to building a robust and resilient DeFi protocol.1


2.2. Core Contract Roles and Responsibilities


Each contract within the architecture has a clearly defined and limited set of responsibilities.


TokenLaunchFactory


         * Role: The central, permissionless deployment hub for all new tokens.
         * Responsibilities:
         * To securely store the platform's treasury address, which will receive the 1% platform fee from all trades across the ecosystem.
         * To implement the public createToken() function, which orchestrates the deployment of new BondingCurveToken instances.
         * To correctly pass all necessary initialization parameters (token name, symbol, creator's address, and the platform's fee address) to the constructor of each new BondingCurveToken contract.
         * To emit a TokenCreated event upon successful deployment. This event is crucial for off-chain services, such as the platform's frontend application, to discover and index new tokens as they are launched.
         * Ownership and Governance: The TokenLaunchFactory contract itself will have an "owner," which should be a secure multi-signature wallet or, in a future iteration, a decentralized autonomous organization (DAO). This ownership provides a secure mechanism for managing platform-level parameters, such as updating the treasury address, without compromising the decentralized nature of the individual token contracts.1


BondingCurveToken


         * Role: A self-contained, multi-purpose contract that serves as both the BEP-20 token and its own dedicated AMM during the initial bonding phase.
         * Responsibilities:
         * To be fully compliant with the BEP-20 token standard by inheriting from a battle-tested, audited implementation, such as OpenZeppelin's ERC20.sol. This ensures compatibility with all standard wallets, explorers, and DeFi protocols on the BNB Chain.1
         * To encapsulate all logic related to its specific market: the bonding curve state variables, the pricing calculation functions, the public buy() and sell() functions, and the 2% fee collection and distribution mechanism.
         * To manage the state machine for its lifecycle, transitioning from the Trading state to the Graduated state upon meeting the graduation threshold.
         * To contain all logic for the automated liquidity provision process, including secure interaction with the PancakeSwap Router contract and the subsequent burning of LP tokens.


2.3. External Protocol Dependencies: PancakeSwap Integration


The protocol's success is contingent on its seamless and secure integration with the broader DeFi ecosystem, specifically PancakeSwap.
         * Target Protocol: The BondingCurveToken contract will be designed to interact exclusively with the PancakeSwap V2 Router. The official V2 Router address on the BNB Chain mainnet (0x10ED43C718714eb63d5aA57B78B54704E256024E) will be hardcoded as an immutable state variable within the contract to prevent any possibility of it being maliciously changed post-deployment.1
         * Interface Definition: The contract will include a minimal interface definition (IPancakeRouter02) that declares the exact function signature for addLiquidityETH. This ensures type safety and guarantees that the contract calls the external protocol with the correct parameters.1
The choice to integrate with the PancakeSwap V2 architecture, which is a direct adaptation of the Uniswap V2 model, is a deliberate risk-mitigation strategy. While newer AMM designs like Uniswap V3 introduce capital efficiency through concentrated liquidity, their complexity is significantly higher. For the protocol's specific use case—a one-time, automated, permanent liquidity provision—the simplicity and robustness of the V2 model are far superior. The V2 architecture has been battle-tested across multiple years and billions of dollars in transaction volume, making it one of the most secure and well-understood pieces of infrastructure in all of DeFi. By building upon this proven foundation, the launchpad protocol minimizes the risk of unforeseen complications or exploits related to its external dependencies.1


Section 3: Contract Specification: TokenLaunchFactory


This section provides the detailed technical blueprint for the TokenLaunchFactory contract. This contract is the immutable entry point to the ecosystem and must be implemented with a focus on simplicity, security, and gas efficiency.


3.1. State Variables and Constructor


The contract's state is minimal, containing only the essential information required for its function.
         * address public immutable platformFeeRecipient;
         * This state variable stores the BNB Chain address of the platform's treasury. It is declared public for transparency and immutable to ensure it is set only once in the constructor. This prevents any future changes, enhancing security and saving gas on subsequent reads.
         * address public allTokens;
         * A dynamic array that stores the contract addresses of every BondingCurveToken deployed by the factory. This provides a simple on-chain mechanism for enumerating all tokens launched on the platform.
         * constructor(address _platformFeeRecipient)
         * The constructor is executed only once, at the time of deployment. Its sole purpose is to initialize the platformFeeRecipient state variable with the address provided during deployment. It must include a check to ensure the provided address is not the zero address.


3.2. Core Functionality: createToken()


This is the primary external function of the factory contract. It is permissionless, allowing any user to launch a new token.
         * function createToken(string memory name, string memory symbol) external returns (address tokenAddress)
         * Visibility: external.
         * Inputs:
         * string memory name: The full name for the new token (e.g., "My Awesome Token").
         * string memory symbol: The ticker symbol for the new token (e.g., "MAT").
         * Logic:
         1. The function first identifies the creator of the token by reading the transaction's origin address (msg.sender).
         2. It then deploys a new instance of the BondingCurveToken contract using Solidity's new keyword.
         3. During instantiation, it passes the required arguments to the BondingCurveToken constructor: the name, the symbol, the creator's address (payable(msg.sender)), and the platform's fee recipient address (payable(platformFeeRecipient)).
         4. The address of the newly created contract is captured in the tokenAddress variable.
         5. This new address is appended to the allTokens array.
         6. Finally, the function emits the TokenCreated event with all relevant details.
         * Returns:
         * address tokenAddress: The contract address of the newly deployed BondingCurveToken.


3.3. Events


Events are crucial for enabling off-chain applications to efficiently track on-chain activity.
         * event TokenCreated(address indexed tokenAddress, address indexed creator, string name, string symbol);
         * This event is emitted every time a new token is successfully created.
         * The tokenAddress and creator parameters are marked as indexed, which allows for efficient filtering and searching by off-chain clients, such as the platform's frontend or data analytics services.


3.4. Access Control and Governance


To ensure the security and long-term maintainability of the platform, the TokenLaunchFactory contract should implement basic access control.
         * Inheritance: The contract should inherit from OpenZeppelin's Ownable.sol.
         * Purpose: While the core createToken() function is and must remain permissionless, establishing an "owner" for the factory contract provides a secure administrative channel. This ownership should be assigned to a multi-signature wallet controlled by the platform's core team or a DAO.
         * Future-Proofing: This ownership pattern allows for future platform-level administrative actions, such as deploying an upgraded version of the factory or managing other platform-wide settings, without compromising the decentralized and immutable nature of the already-deployed token contracts.


Section 4: Contract Specification: BondingCurveToken


This section provides an exhaustive specification for the BondingCurveToken contract. This is the operational heart of the system, and its implementation must adhere to the highest standards of security and precision.


4.1. Part I: Inheritance, State, and Initialization


The contract's foundation is built upon standard, audited components and a carefully defined set of state variables.
         * Inheritance: contract BondingCurveToken is ERC20, Ownable
         * The contract will inherit from @openzeppelin/contracts/token/ERC20/ERC20.sol to ensure full BEP-20 compliance.1
         * It will inherit from @openzeppelin/contracts/access/Ownable.sol. In this context, Ownable is used for a specific, limited purpose: to ensure that critical, one-time initialization actions can be performed securely before ownership is permanently renounced during the graduation phase.
         * State Variables:
         * Bonding Curve Constants:
         * uint256 public constant VIRTUAL_BNB_RESERVES = 30 ether;
         * uint256 public constant VIRTUAL_TOKEN_RESERVES = 1073000191 * 1e18;
         * uint256 public constant K = VIRTUAL_BNB_RESERVES * VIRTUAL_TOKEN_RESERVES;
         * Live State:
         * uint256 public bnbReserves;: Tracks the real BNB collected from buyers, which will be used for liquidity.
         * Fee Parameters:
         * address payable public immutable creator;: The token creator's address.
         * address payable public immutable platformFeeRecipient;: The platform's treasury address.
         * Lifecycle State:
         * enum Status { Trading, Graduated }: A state machine to control the contract's phase.
         * Status public status;: The current status of the token lifecycle.
         * DEX Integration:
         * IPancakeRouter02 public immutable pancakeRouter;: An interface to the PancakeSwap V2 Router.
         * address public pancakePair;: Stores the address of the created PancakeSwap pair after graduation.
         * Constructor:
         * constructor(string memory name, string memory symbol, address payable _creator, address payable _platformFeeRecipient) ERC20(name, symbol) Ownable(msg.sender)
         1. The ERC20 constructor is called with the token's name and symbol.
         2. The Ownable constructor is called, initially setting the deploying factory contract as the owner.
         3. The immutable creator and platformFeeRecipient addresses are set.
         4. The pancakeRouter address is initialized with the official PancakeSwap V2 Router address for BNB Chain.
         5. The total supply of 1 billion tokens is minted and assigned to the contract itself: _mint(address(this), TOTAL_TOKEN_SUPPLY). The contract acts as the initial holder of all tokens that will be sold on the curve.
         6. The initial status is set: status = Status.Trading;.


4.2. Part II: Internal Pricing Logic


These internal functions encapsulate the core mathematics of the bonding curve. They are not exposed publicly but are used by the buy and sell functions.
         * function getAmountOfTokens(uint256 bnbAmount) internal view returns (uint256): This function implements the pricing formula specified in Section 1.1 to calculate the exact number of tokens a user should receive for a given amount of BNB. It must use the sum of bnbReserves and VIRTUAL_BNB_RESERVES for its calculation.
         * function getAmountOfBNB(uint256 tokenAmount) internal view returns (uint256): This function implements the inverse formula to calculate the amount of BNB a user should receive when selling a specific quantity of tokens.


4.3. Part III: Core Interaction Functions (buy and sell)


These functions are the public interface for trading during the bonding phase. Their implementation must strictly follow the Checks-Effects-Interactions security pattern to prevent re-entrancy attacks.1
         * function buy(uint256 minTokensOut) external payable
         1. Checks:
         * require(status == Status.Trading, "Trading is not active");
         * require(msg.value > 0, "BNB amount must be positive");
         2. Calculations (Effects Part 1):
         * Calculate platformFee and creatorFee (1% each) from msg.value.
         * Calculate bnbToReserve as msg.value minus the total fees.
         * Calculate tokensToMint by calling getAmountOfTokens(bnbToReserve).
         * require(tokensToMint >= minTokensOut, "Slippage limit exceeded");
         3. Effects (State Changes):
         * Increment bnbReserves by bnbToReserve.
         * Transfer the tokensToMint from the contract's own balance to the buyer (msg.sender). This is done via super._transfer(address(this), msg.sender, tokensToMint).
         * Check if bnbReserves has now crossed the GRADUATION_THRESHOLD_BNB. If it has, update the state: status = Status.Graduated;.
         4. Interactions (External Calls):
         * Transfer the platformFee to platformFeeRecipient.
         * Transfer the creatorFee to creator.
         * These transfers must use low-level .call{value:...}("") with checks on the return value to handle potential failures gracefully.
         * function sell(uint256 tokensToSell, uint256 minBnbOut) external
         1. Checks:
         * require(status == Status.Trading, "Trading is not active");
         * require(tokensToSell > 0, "Token amount must be positive");
         2. Calculations (Effects Part 1):
         * Calculate the gross bnbToReturn by calling getAmountOfBNB(tokensToSell).
         * require(bnbToReturn <= bnbReserves, "Insufficient BNB reserves");
         * Calculate platformFee and creatorFee from bnbToReturn.
         * Calculate the finalBnbAmount to be sent to the user.
         * require(finalBnbAmount >= minBnbOut, "Slippage limit exceeded");
         3. Effects (State Changes):
         * Decrement bnbReserves by the full bnbToReturn amount.
         * Transfer the tokensToSell from the seller (msg.sender) to the contract (address(this)).
         4. Interactions (External Calls):
         * Transfer fees to the platform and creator.
         * Transfer the finalBnbAmount to the seller (msg.sender).


4.4. Part IV: The Graduation Mechanism


This function executes the final, trust-minimized step of the token's lifecycle on the launchpad.
         * function graduateToPancakeSwap() external
         1. Checks:
         * require(status == Status.Graduated, "Not ready for graduation");
         * require(pancakePair == address(0), "Liquidity already added"); This ensures the function can only be successfully executed once.
         2. Calculations:
         * Determine the bnbForLiquidity (e.g., 75% of bnbReserves).
         * Determine the tokensForLiquidity to pair with the BNB, based on the final price on the bonding curve.
         3. Effects & Interactions Sequence:
a. Approve the PancakeSwap Router to spend the contract's tokens: _approve(address(this), address(pancakeRouter), tokensForLiquidity).
b. Call pancakeRouter.addLiquidityETH{value: bnbForLiquidity}(...). The parameters will include the token address, the amount of tokens and BNB, deadlines, and the recipient address (address(this)). This call returns the address of the newly created LP pair contract.
c. Store the returned pair address in the pancakePair state variable.
d. Query the contract's new balance of PancakeSwap LP tokens.
e. Burn LP Tokens: Immediately execute a transfer of the entire LP token balance to the burn address (0x00...dEaD). This is a non-negotiable security step.1
f. Renounce Ownership: Call the internal _transferOwnership(address(0)) function (from Ownable.sol) to permanently burn the ownership keys, making the contract fully immutable and trustless.


4.5. Fee Implementation Mandate: Avoiding the Fee-on-Transfer Anti-Pattern


A critical design constraint of this protocol is the method of fee implementation. A common but deeply flawed approach for "tax tokens" is to override the standard _transfer function to deduct a fee on every token movement. This is a known anti-pattern that renders a token incompatible with standard AMMs like PancakeSwap.1 AMMs operate on the strict assumption that the amount of tokens they send is the exact amount that arrives at the destination. A fee-on-transfer mechanism violates this assumption, leading to internal accounting errors, failed transactions, and potential economic exploits within the liquidity pool.
Given that the entire purpose of this protocol's lifecycle is to successfully list the token on PancakeSwap, implementing a fee-on-transfer model would be self-sabotage.
Therefore, this specification mandates the following:
            1. The BondingCurveToken contract must not override or modify the standard _transfer or _transferFrom functions inherited from OpenZeppelin's ERC20.sol.
            2. The 2% transaction fee is to be implemented exclusively within the logic of the buy() and sell() functions.
            3. Since these functions are permanently disabled after the token graduates to PancakeSwap, the fee mechanism is confined to the initial bonding curve phase. Once trading moves to PancakeSwap, the token will behave as a standard, fee-free BEP-20 token, subject only to PancakeSwap's own trading fees. This ensures full compatibility with the broader DeFi ecosystem.


Section 5: Security Framework and Trust-Minimization Protocols


Security is the paramount concern in the design of this protocol. This section outlines the non-negotiable security procedures, analyzes potential vulnerabilities, and provides a comprehensive mitigation strategy.


5.1. Non-Negotiable Security Procedures (Post-Graduation)


The following actions are mandatory and must be executed programmatically within the graduateToPancakeSwap function to establish a trustless environment for the token post-launch.
            * LP Token Burning: 100% of the PancakeSwap LP tokens received by the contract after providing liquidity must be transferred to a known burn address in the same transaction. This is the single most important defense against liquidity-based rug pulls.1
            * Renouncing Ownership: The contract's ownership, initially held by the factory, must be permanently renounced by transferring it to the zero address. This prevents any future malicious administrative actions, such as pausing the contract, minting new tokens, or introducing backdoors.1
            * Disabling Core Functions: The buy() and sell() functions must be irreversibly disabled by the state transition to Graduated. This ensures the bonding curve mechanism cannot be tampered with or reactivated after the public DEX listing.


5.2. Vulnerability Analysis and Mitigation


The protocol's design incorporates defenses against several common DeFi attack vectors.
            * Re-entrancy: This is the most critical threat to contracts that handle fund transfers. Mitigation is achieved by strictly adhering to the Checks-Effects-Interactions pattern in both the buy() and sell() functions. All internal state changes (e.g., updating reserves, transferring tokens) are completed before any external calls are made to transfer BNB to the creator, platform, or seller.1
            * Front-Running and Slippage: Malicious actors in the mempool can exploit pending transactions. This is mitigated by requiring users to provide minTokensOut (for buys) and minBnbOut (for sells) parameters. These act as a slippage tolerance control. If the price moves unfavorably before the transaction is mined, the requirement check will fail, and the transaction will revert, protecting the user from significant losses.1
            * Integer Overflow/Underflow: By mandating the use of Solidity compiler version ^0.8.0 or higher, the protocol leverages built-in checked arithmetic. The compiler will automatically cause a transaction to revert if any arithmetic operation results in an overflow or underflow, eliminating an entire class of historical vulnerabilities.1
            * Price Oracle Manipulation: The price on a bonding curve can be manipulated significantly within a single transaction block. Therefore, it must be explicitly stated in all documentation that this bonding curve should not be used as a reliable price oracle by any other DeFi protocol. External protocols should use Time-Weighted Average Price (TWAP) oracles from the post-graduation PancakeSwap pool instead.1

6.2. Deployment Scripts


A Hardhat script automates the deployment process, ensuring it is repeatable and less prone to manual error.
               * Deployment Script (scripts/deploy.js):
This script deploys the TokenLaunchFactory contract.
JavaScript
// scripts/deploy.js
const hre = require("hardhat");

async function main() {
 const [deployer] = await hre.ethers.getSigners();
 console.log("Deploying contracts with the account:", deployer.address);

 const platformFeeRecipientAddress = "PLATFORM_TREASURY_MULTI_SIG_ADDRESS"; // IMPORTANT: Replace with the actual platform treasury address

 const TokenLaunchFactory = await hre.ethers.getContractFactory("TokenLaunchFactory");
 const factory = await TokenLaunchFactory.deploy(platformFeeRecipientAddress);

 await factory.waitForDeployment();

 const factoryAddress = await factory.getAddress();
 console.log("TokenLaunchFactory deployed to:", factoryAddress);
}

main().catch((error) => {
 console.error(error);
 process.exitCode = 1;
});

               * Execution Command:
Bash
npx hardhat run scripts/deploy.js --network bscTestnet



6.3. Contract Verification


Source code verification on a block explorer like BscScan is a critical step for transparency and user trust. It allows anyone to read and audit the deployed contract's code.
                  * Procedure: After a successful deployment, use the @nomicfoundation/hardhat-verify plugin (included in hardhat-toolbox) to programmatically verify the contract.
                  * Verification Command:
Bash
npx hardhat verify --network bscTestnet DEPLOYED_FACTORY_ADDRESS "PLATFORM_TREASURY_MULTI_SIG_ADDRESS"

Replace DEPLOYED_FACTORY_ADDRESS with the address output by the deployment script and provide the same constructor argument used during deployment. This command will upload the source code and ABI to BscScan, linking it to the on-chain bytecode. The BondingCurveToken implementation contract should also be verified so that users can inspect the template logic.
